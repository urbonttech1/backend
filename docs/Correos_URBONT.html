📧 Sistema de Correos - URBONT API

Fecha: Septiembre 2026

Versión: 1.2.2

📋 Resumen Ejecutivo

La plataforma URBONT envía correos electrónicos en 3 escenarios principales:

  1. Recibos de viaje completado (pasajeros)
  2. Notificaciones de soporte (admin)
  3. Códigos OTP de verificación (usuarios)

1️⃣ Recibo de Viaje (Trip Receipt)

Información General

Parámetro Valor
Cuándo se envía Al completar un viaje
Destinatario Email del pasajero
Proveedor ✓ Resend
Archivo server/services/email.ts:123
Base de datos rides.receipt_sent (boolean)

Contenido del Correo

  • Encabezado con branding URBONT
  • Ruta: Pickup → Dropoff (con paradas si aplica)
  • Detalles del conductor: Nombre y vehículo
  • Métricas del viaje:
    • Distancia (en millas)
    • Duración (en minutos)
    • Método de pago
  • Desglose de tarifa:
    • Tarifa base
    • Descuento de promo (si aplica)
    • Propina (si aplica)
    • Total cobrado
  • ID del viaje para referencia

Configuración Requerida

RESEND_API_KEY=re_xxxxxxxxxxxxx EMAIL_FROM=URBONT <receipts@urbont.app>

Comportamiento

  • ✓ Si RESEND_API_KEY está configurado → se envía automáticamente
  • ⚠️ Si no está configurado → se registra warning, pero el viaje se completa normalmente

2️⃣ Tickets de Soporte

Información General

Parámetro Valor
Cuándo se envía Cuando usuario abre un ticket de soporte
Destinatario Email del administrador (ADMIN_EMAIL)
Proveedor ⚠ SMTP (nodemailer)
Archivo server/api/support.ts:30-104

Contenido del Correo

  • Categoría del problema:
    • Lost Item (Artículo perdido)
    • Driver Issue (Problema con conductor)
    • Billing (Facturación)
    • App Issue (Problema con app)
    • Safety (Seguridad)
    • Other (Otro)
  • Prioridad: Low, Normal, High, Urgent (con código de color)
  • Datos del usuario: Nombre y teléfono
  • Asunto y descripción detallada
  • ID del viaje (si está relacionado con un viaje)
  • Timestamp en zona horaria America/New_York

Configuración Requerida

SMTP_HOST=smtp.gmail.com SMTP_PORT=587 SMTP_USER=tu-email@gmail.com SMTP_PASS=tu-password-o-app-key ADMIN_EMAIL=admin@urbont.com

Comportamiento

  • ✓ Si SMTP está completamente configurado → se envía al admin
  • ⚠️ Si faltan variables → warning en logs, ticket se crea pero no se notifica

3️⃣ Código OTP (One-Time Password)

Información General

Parámetro Valor
Cuándo se envía Usuario solicita código de verificación para login
Destinatario Email del usuario
Proveedor ⚠ SMTP (nodemailer)
Archivo server/api/auth/otp.ts:140-160
Expiración 10 minutos

Contenido del Correo

  • Branding URBONT
  • Código de 6 dígitos prominente
  • Instrucción de usar el código en la app
  • Aviso de confidencialidad
  • Aviso de expiración (10 minutos)

Configuración Requerida

Mismas variables que Soporte (SMTP completo)

SMTP_HOST=smtp.gmail.com SMTP_PORT=587 SMTP_USER=tu-email@gmail.com SMTP_PASS=tu-password-o-app-key

Comportamiento

  • ✓ Si SMTP está configurado → se envía código
  • ⚠️ Si SMTP no está → warning, pero login puede continuar (según implementación)
  • El código se almacena en memoria (otpStore) con timestamp de expiración

⚙️ Flujo de Funcionamiento

Recibo de Viaje

  1. Viaje marcado como "completed" en rides.ride_status
  2. Sistema llama a sendRideReceipt() con datos del viaje
  3. Si RESEND_API_KEY existe → envía vía Resend
  4. Actualiza rides.receipt_sent = true
  5. Si falla → log warning, viaje sigue completado

Ticket de Soporte

  1. Usuario crea ticket POST /api/support/tickets
  2. Ticket se guarda en BD (support_tickets)
  3. Sistema llama a sendAdminEmail()
  4. Si SMTP está configurado → envía al admin
  5. Si falla → log warning, ticket sigue creado

OTP

  1. Usuario solicita código GET /api/auth/otp?email=...
  2. Sistema genera código de 6 dígitos
  3. Guarda en otpStore con expiración (10 min)
  4. Si SMTP está configurado → envía código por email
  5. Usuario verifica código en app antes de expiración

⚠️ Notas Importantes

  • Fallos no bloqueantes: Si SMTP o Resend fallan, el flujo continúa (viaje se completa, ticket se crea, login continúa). Solo se registra warning.
  • Resend vs SMTP: Resend para recibos (proveedor dedicado), SMTP para notificaciones internas (más económico).
  • OTP en memoria: Los códigos se almacenan en un Map en memoria. Si el servidor reinicia, se pierden los códigos pendientes.
  • Spam: No hay rate limiting para envío de OTP. Implementar si se reciben ataques de spam.
  • HTML emails: Todos los correos son HTML formateados. Clientes de email debe soportar HTML.
