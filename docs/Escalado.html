Escalado de la API

Cómo aumentar la capacidad del servicio: cuándo hacerlo, qué comandos ejecutar, cómo verificar que funcionó y cómo revertirlo.

Servicio: urbont-api · cluster urbont Región: us-east-1 · perfil urbont Actualizado: 7 sep 2026

1.Punto de partida

ParámetroValor actualNota
Contenedores1Fijo. No cambia solo.

ArquitecturaARM64Debe coincidir con el --platform del build

Lo primero que hay que entender

Ante un pico de tráfico no pasa nada automáticamente. El servicio se satura, responde lento y termina rechazando peticiones. Nadie recibe una alerta. Escalar es hoy una acción manual y hay que decidirla mirando las métricas.

2.Cuándo escalar

Decisión basada en el uso sostenido del procesador, no en sensaciones.

ProcesadorEquivale aAcción
bajo 40%hasta ~6 pet/s Ninguna. Es la situación actual.
40% a 70%~6 a 11 pet/s Escalar vertical (sección 3). Planificarlo, no urge.
sobre 70%más de 11 pet/s Escalar ya. Por encima del 85% aparecen tiempos de espera.

Consultar el estado actual

# Uso del procesador — últimas 24 horas
aws cloudwatch get-metric-statistics --region us-east-1 --profile urbont \
  --namespace AWS/ECS --metric-name CPUUtilization \
  --dimensions Name=ClusterName,Value=urbont Name=ServiceName,Value=urbont-api \
  --start-time "$(date -u -v-24H '+%Y-%m-%dT%H:%M:%S')" \
  --end-time "$(date -u '+%Y-%m-%dT%H:%M:%S')" \
  --period 3600 --statistics Average Maximum \
  --query 'Datapoints[].{hora:Timestamp,prom:Average,max:Maximum}' --output table

Los umbrales salen de una medición del 7 de septiembre de 2026: con 2,49 pet/s el procesador llegó a 17,3%, o sea unos 6 puntos porcentuales por petición/segundo. Conviene recalcularlos si cambia el perfil de tráfico.

3.Escalado vertical

Agrandar el contenedor. Disponible hoy, sin tocar código.

Combinaciones válidas

Fargate solo acepta ciertos pares. Un valor fuera de la tabla es rechazado al registrar:

cpuEquivale amemory admitida
2560,25 vCPU512, 1024, 2048
5120,5 vCPU actual1024 a 4096, de 1024 en 1024
10241 vCPU2048 a 8192
20482 vCPU4096 a 16384
40964 vCPU8192 a 30720

Editar taskdef.json

{
  "cpu": "1024",      // antes: "512"
  "memory": "2048",   // antes: "1024"
  ...
}

Registrar la revisión nueva

aws ecs register-task-definition --cli-input-json file://taskdef.json \
  --region us-east-1 --profile urbont \
  --query 'taskDefinition.revision' --output text

Devuelve el número de revisión. Anotarlo: hace falta en el paso siguiente.

Aplicarla al servicio

# reemplazar 3 por la revisión que devolvió el paso anterior
aws ecs update-service --cluster urbont --service urbont-api \
  --task-definition urbont-api:3 --force-new-deployment \
  --region us-east-1 --profile urbont

Esperar y verificar

Tarda 60 a 120 segundos. Ver la sección 6.

Al reducir el tamaño, vigilar el arranque

El arranque ejecuta migraciones y verifica el esquema antes de aceptar tráfico, con un startPeriod de 40 segundos. Con menos procesador ese arranque se alarga y puede superar el límite, provocando que ECS mate el contenedor y reintente en bucle. Si se baja a 256, revisar los registros del primer despliegue.

4.Escalado horizontal

Agregar contenedores. Bloqueado hasta resolver cuatro obstáculos.

No ejecutar todavía

Subir el número de contenedores hoy rompe el servicio de forma silenciosa: no falla nada visible, pero los viajes empiezan a asignarse dos veces. Los fallos son intermitentes y no dejan error en los registros.

Qué hay que resolver primero

#ProblemaEfecto con 2 o más contenedores
1Tareas programadas sin guarda Los 14 trabajos se ejecutan duplicados. El peor: el que reasigna viajes abandonados los asigna a dos conductores distintos.
2Registro de conductores en memoria El conductor conectado al otro contenedor no recibe la oferta de viaje.
3Límite de peticiones en memoria El límite se multiplica por el número de contenedores.
4Temporizadores del proceso Reasignaciones pendientes se pierden al reciclar un contenedor.

El detalle trabajo por trabajo está en docs/CRON_JOBS.md y en el anexo de docs/AWS_ECS_DEPLOY.md.

Una vez resueltos

Levantar la caché compartida

Obligatoria: es lo que permite que los contenedores compartan estado.

aws elasticache create-cache-cluster \
  --cache-cluster-id urbont-redis \
  --engine valkey --cache-node-type cache.t4g.micro \
  --num-cache-nodes 1 --security-group-ids <SG_TASK> \
  --region us-east-1 --profile urbont

Añadir REDIS_URL al entorno, reconstruir la imagen y desplegar.

Subir el número de contenedores

aws ecs update-service --cluster urbont --service urbont-api \
  --desired-count 2 --region us-east-1 --profile urbont
Ya está preparado para esto

El balanceador tiene sesiones pegajosas activadas y un tiempo de espera de 300 segundos, configurados desde el despliegue inicial precisamente para este momento. El seguimiento en vivo seguirá funcionando al repartir el tráfico entre contenedores.

5.Autoescalado

Que AWS ajuste el número de contenedores sin intervención. Requiere la sección 4 resuelta.

Requisito previo

Activarlo antes de resolver los cuatro obstáculos hace que el sistema se rompa solo justo cuando llega la carga, que es el peor momento posible.

Registrar el rango permitido

aws application-autoscaling register-scalable-target \
  --service-namespace ecs \
  --resource-id service/urbont/urbont-api \
  --scalable-dimension ecs:service:DesiredCount \
  --min-capacity 2 --max-capacity 6 \
  --region us-east-1 --profile urbont

min-capacity 2 mantiene la tolerancia a fallos incluso sin tráfico.

Definir la política

cat > /tmp/scaling.json <<'JSON'
{
  "TargetValue": 60.0,
  "PredefinedMetricSpecification": {
    "PredefinedMetricType": "ECSServiceAverageCPUUtilization"
  },
  "ScaleOutCooldown": 60,
  "ScaleInCooldown": 300
}
JSON

aws application-autoscaling put-scaling-policy \
  --service-namespace ecs \
  --resource-id service/urbont/urbont-api \
  --scalable-dimension ecs:service:DesiredCount \
  --policy-name urbont-api-cpu \
  --policy-type TargetTrackingScaling \
  --target-tracking-scaling-policy-configuration file:///tmp/scaling.json \
  --region us-east-1 --profile urbont
ParámetroValorPor qué
TargetValue60% Deja margen para que el contenedor nuevo arranque antes de saturarse.
ScaleOutCooldown60 s Crecer rápido: es preferible pagar de más un rato que rechazar peticiones.
ScaleInCooldown300 s Reducir lento, para no oscilar entre agregar y quitar contenedores.
max-capacity6 Tope de gasto. Con 6 contenedores la factura ronda los $270 mensuales.

Comprobar que quedó activo

aws application-autoscaling describe-scaling-policies \
  --service-namespace ecs --region us-east-1 --profile urbont \
  --query 'ScalingPolicies[].{politica:PolicyName,recurso:ResourceId}' --output table

6.Verificar

# Estado del despliegue — debe quedar un solo despliegue PRIMARY
# con Running igual a Desired y Pending en 0
aws ecs describe-services --cluster urbont --services urbont-api \
  --query 'services[0].deployments[*].{Estado:status,Corriendo:runningCount,Pendiente:pendingCount}' \
  --output table --region us-east-1 --profile urbont

# Que el balanceador vea el contenedor sano
TG=$(aws elbv2 describe-target-groups --names urbont-api-tg \
  --query 'TargetGroups[0].TargetGroupArn' --output text \
  --region us-east-1 --profile urbont)
aws elbv2 describe-target-health --target-group-arn $TG \
  --query 'TargetHealthDescriptions[].TargetHealth.State' \
  --output text --region us-east-1 --profile urbont

# Prueba real de punta a punta
curl -s https://api.urbont.com/api/healthz

Si algo queda en Pending más de dos minutos, revisar los eventos del servicio:

aws ecs describe-services --cluster urbont --services urbont-api \
  --query 'services[0].events[:5].message' --output table \
  --region us-east-1 --profile urbont

7.Revertir

Volver al tamaño anterior

# listar revisiones disponibles
aws ecs list-task-definitions --family-prefix urbont-api --sort DESC \
  --region us-east-1 --profile urbont

# volver a la anterior
aws ecs update-service --cluster urbont --service urbont-api \
  --task-definition urbont-api:2 --force-new-deployment \
  --region us-east-1 --profile urbont

Volver a un solo contenedor

aws ecs update-service --cluster urbont --service urbont-api \
  --desired-count 1 --region us-east-1 --profile urbont

Desactivar el autoescalado

aws application-autoscaling delete-scaling-policy \
  --service-namespace ecs --policy-name urbont-api-cpu \
  --resource-id service/urbont/urbont-api \
  --scalable-dimension ecs:service:DesiredCount \
  --region us-east-1 --profile urbont

Toda la operación es reversible y sin caída de servicio: la configuración de despliegue (100% mínimo sano, 200% máximo) levanta el contenedor nuevo y espera a que pase el chequeo de salud antes de retirar el anterior.

8.Costo de cada paso

PasoConfiguración Peticiones/sMensualRequisito
Actual1 × 0,5 vCPUhasta ~11 $48—
Vertical1 × 1 vCPUhasta ~22 $63Configuración
Horizontal2 × 0,5 vCPUhasta ~22 $78Desarrollo
Consolidado4 × 1 vCPU~85 $199Desarrollo

Vertical y horizontal cuestan parecido y sostienen tráfico parecido. La diferencia real es que el horizontal tolera fallos: si un contenedor cae, el otro sigue atendiendo. El vertical no da esa garantía por más grande que sea.
